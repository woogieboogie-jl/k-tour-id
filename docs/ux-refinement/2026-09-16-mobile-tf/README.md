## 요청과 범위

전체 페이지·단계·복귀 흐름을 먼저 목록화한 뒤, 모바일 타이포·간격·정보 위계·행동 배치·시트 조합을 검수했다. 결과는 화면별로 **반드시 수정 / 개선 권장 / 유지 / 검수 한계**를 구별하고, 구체적인 수정안과 보존할 기능을 남겼다. 이후 사용자 승인에 따라 각 항목을 순차 구현하고 독립 검토 후 다음 항목으로 이동했다. GitHub push·배포·외부 provider 실행은 하지 않았다.

직전 제보인 둥근 바텀시트 코너의 사각 배경은 먼저 독립 재현 후 공통 Sheet CSS를 로컬 수정했다. 아래 코너 결과는 그 선행 빌드의 기록이며 이후22개 항목의 최종 결과와 합산하지 않는다.

## 절차와 증거

1. 현행 코드와 과거 sitemap을 대조해 페이지/step/terminal/return 목록 동결. 새 스탬프 화면 포함. URL 수·상태 enum 수를 화면 검수 수로 부르지 않는다.
2. 390×844를 주 구성으로 실제 경로를 확인하고, 320px/430px, 긴 KO/EN/JA, 다크 모드에서 리스크를 재확인한다. 대표 위험 화면은 짧은 높이·텍스트 확대도 확인한다.
3. 스크린샷 + 실제 font-size/line-height/inset/버튼 높이 + 진입/복귀 근거를 남긴다. 정상·빈 상태·실패·취소·복귀는 다른 상태로 센다.
4. 서로의 필수 수정안을 반대 관점에서 검토한다. 취향 차이를 결함으로 부풀리지 않고, 기능을 없애는 제안은 PRD 근거와 대체 진입을 함께 적는다.
5. 화면별 수정 정의, 공통 컴포넌트 우선순위, 미검수/실연동 한계를 최종 목록으로 전달한다.

브라우저 검수는 동시 worker 합계2개 이하로 운영한다. 최종 검수는 고정 artifact를 공유하며 실행 중 rebuild로 증거가 섞이지 않게 한다. 외부 identity/payment/wallet/chain 요청과 원격 mutation을 차단한다. `review=0`과 공개 샘플 경로를 구분하며, 테스트용 상태 주입을 일반 사용자의 도달 증거로 사용하지 않는다.

## 코너 결함 · 확인된 원인

`SheetB` 바깥 section의 radius/overflow는 정상이나, 헤더가 radius 0의 반투명 `backdrop-filter` 레이어라 둥근 잘림 밖에 사각 픽셀을 그린다. 픽셀의 클릭 대상은 여전히 backdrop이므로 기존 bounds/hit/focus 검사는 이 결함을 통과시킨다.

수정: 비스크롤 헤더/푸터에서 불필요한 blur를 제거하고 같은 표면 색과 해당 모서리 radius를 소유하게 했다. sheet 전체를 강제 mask해 그림자·포커스 링을 잘라내는 방식은 쓰지 않는다. 820px light의 실제 방문 시트에서 수정 전 코너 픽셀 차이 188로 새 회귀 검사가 실패하는 것을 확인했다(허용 12).

수정 후 `ktour-sheet-corner-paint.spec.ts`는 320/390/820/1440 × light/dark **8개 actual case 통과**(project에 맞지 않는 skip 8개 별도). 각 case에서 방문 진입·저장 후·컬렉션 양쪽 모서리를 비교했다. 공유 Sheet 계약 6개·typecheck·로컬 build/scanner도 통과. 앱 로직 JS는 `page-073dddfa315a0782.js`로 같지만 CSS가 바뀌었으므로 이후 캡처 JSON에는 실제 로드된 CSS resource도 함께 보존한다.

다른 전용 시트의 같은 패턴은 아직 코드상 후보이며, 화면에서 재현하기 전 확정 결함이라고 부르지 않는다.

코드 목록을 먼저 대조한 뒤 디자이너 역할 에이전트 3명이 새 로컬 화면을 나눠 검수했고, 서로의 결함/개선안을 실제 이미지와 PRD 기준으로 반대 검토했다. D1 53, D2 73, D3 191, 코디네이터 최종75개의 화면·스타일 자료를 남겼다. **392개 캡처는392개 고유 페이지나392개 PASS가 아니다.** 미확인 상태와 실제 provider/실기기 범위는 각 보고서 및 coverage에 명시했다.
